Why SecScore

Built to reduce AppSec friction, not increase it.

01

Policy-driven scoring

Security logic lives in policy, not in the scanner. Tune thresholds, penalties, hard fails and ignored paths to match your reality.

02

SARIF first

Use the standard format most modern scanners already support. Less vendor lock-in. Less brittle integration.

03

Made for Pull Requests

Score PRs, comment on findings, update status checks and support branch protection without turning the pipeline into a circus.

04

Open-source core

Keep the engine transparent, inspectable and scriptable. No black-box scoring nonsense pretending to be science.

05

Noise control

Ignore paths like node_modules, vendor, dist and other junk your team should not be penalized for.

06

Security decisions, fast

Teams do not need more dashboards. They need a clear answer in the PR. SecScore gives one.

What makes it different

Severity alone is lazy. Pipelines need context and thresholds.

A scanner says “there is a finding”. SecScore answers the only question that matters in a delivery workflow:

“Does this Pull Request deserve to pass, require review, or fail?”

  • Single score from multiple findings
  • Hard-fail rules for critical cases
  • Support for provider mode and SARIF mode
  • Designed to work with GitHub Actions, but not only.
Minimal usage example 
- name: Run SecScore
            uses: cassiodeveloper/SecScore@v0.1.0
            with:

Provider mode example 
- name: Run SecScore
            uses: cassiodeveloper/SecScore@v0.1.0
            with:
                provider: checkmarx
                checkmarx-project: ${{ secrets.CX_PROJECT }}
                checkmarx-base-url: ${{ secrets.CX_BASE_URL }}

FAQ

Fast answers for people who hate wasting time.

Is SecScore a scanner?

No. SecScore is a decision engine. It consumes findings from scanners and calculates a score plus a final PR decision.

Does it work only with Checkmarx?

No. SARIF is the preferred path, which makes SecScore compatible with multiple scanners. Checkmarx API support is just one provider mode.

Can I define my own security policy?

Yes. The score, thresholds, penalties, hard-fail rules and ignored paths are all policy-driven.

Can it be used with branch protection?

Yes. That is one of the core use cases: publish a status check and use it in GitHub branch protection rules.
